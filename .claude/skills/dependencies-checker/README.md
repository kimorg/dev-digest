# Dependencies checker skill

**Version:** 1.0.0 · **Scope:** every package of the repo (`server`, `client`, `reviewer-core`,
`mcp`, `e2e`, `evals` — any tracked `package.json` outside `.claude/`, fixtures and clones).

## Motivation

The repo is five-plus standalone packages with two package managers, source shared through
tsconfig aliases and a contract package vendored twice. Nobody sees the whole dependency picture:
which package pulls 400 MB, which library is declared but unused, which one is imported without
being declared, where `zod` or `vitest` drifted, and what to fix first. Generic tools answer one
question each (`npm audit`, `depcheck`, `du`) and none of them knows about the aliases or the
vendored copies. This skill gives one structured report with a map, numbers and a plan.

## Positions taken

| Question | Position | Why |
|---|---|---|
| Who computes the facts? | A deterministic, dependency-free Node script (`scripts/collect.mjs`) | Numbers must be reproducible and cheap (~1 s offline); the model is bad at counting bytes and good at judging findings |
| Where do sizes come from? | The installed `node_modules`, resolved the way Node resolves (pnpm store and npm hoisting) | Lockfile parsers differ per manager; the installed tree is what actually runs, and it needs no network |
| Which size? | Own, **closure** and **exclusive** (closure minus what any other direct dependency also needs) | Exclusive is the honest "what removal frees" number; closure alone double-counts shared packages |
| Bundle size? | Not measured; install size only, `browser` flag for `'use client'` imports | Real bundle size needs `next build`; promising bundle wins from install sizes would mislead |
| How is usage found? | Regex scan of tracked + untracked source, config and style files; bins in npm scripts; package-name strings in config files; peers; `@types` targets | A parser per file type is slow and heavy; the false positives are known and listed per rule with a check |
| Who decides priority? | The rule gives a default; the agent may change it only with a reason from `prioritization.md` and records it in the *Triage* column | Deterministic baseline + auditable judgement; no silent drops |
| Network? | Offline by default; `--online` adds `audit` + `outdated` of each package's own manager | Sending the tree to the registry is an outward action; the user opts in |
| Diagrams? | Mermaid generated by the script, validated with the real Mermaid parser (`check-mermaid.mjs`) | Renders on GitHub and in IDEs; generated text never has hand-made syntax errors |
| Output? | Fixed-section Markdown in `docs/deps/` + a fixed-shape chat summary | Developers diff reports between dates; the chat answer stays short |

## Layout

```
dependencies-checker/
├── SKILL.md                     procedure, hard rules, output contract
├── README.md                    this file
├── references/
│   ├── report-template.md       sections, columns, slot shapes with examples
│   ├── rules.md                 every rule: detects, default priority, false positives, check, fix
│   └── prioritization.md        P0–P3, when to re-prioritise, effort, gain, plan ordering
└── scripts/
    ├── collect.mjs              CLI: scan → deps.json (schema 1) + deps.md (report skeleton)
    ├── check-mermaid.mjs        parses every mermaid block with client/'s mermaid + jsdom
    ├── lib/
    │   ├── scan.mjs             node_modules resolution, sizes, closures (I/O)
    │   ├── usage.mjs            imports, file contexts, categories, licenses (pure)
    │   ├── semver.mjs           range satisfaction without dependencies (pure)
    │   ├── rules.mjs            findings + cross-package drift (pure)
    │   ├── render.mjs           Markdown + Mermaid (pure)
    │   └── online.mjs           audit / outdated runners + normalisers
    └── lib.test.mjs             node:test unit tests
```

## Commands

All skill arguments and collector options, with defaults: [SKILL.md § Usage](SKILL.md#usage).

```sh
node .claude/skills/dependencies-checker/scripts/collect.mjs --json t/deps.json --md t/deps.md   # offline, ~1 s
node .claude/skills/dependencies-checker/scripts/collect.mjs --online --json t/deps.json --md t/deps.md   # + registry, ~20 s
node .claude/skills/dependencies-checker/scripts/collect.mjs --packages server,reviewer-core --md t/deps.md
node .claude/skills/dependencies-checker/scripts/check-mermaid.mjs t/deps.md
node --test .claude/skills/dependencies-checker/scripts/lib.test.mjs
```

## Adding a rule

1. `scripts/lib/rules.mjs`: add the id and title to `RULES`, emit it in `buildFindings` with a
   default priority, evidence and fix (thresholds go into `THRESHOLDS`).
2. If it needs a new fact, collect it in `collect.mjs` (per dependency or per package) — keep
   `lib/*` pure where possible.
3. `references/rules.md`: a section with *Detects*, *Default*, *False positives* + *Check*, *Fix*;
   and the rule in the right row of `references/prioritization.md`.
4. A test in `lib.test.mjs` with a synthetic model (see the `rules:` tests).
5. Run the collector on the repo and `check-mermaid.mjs` on the output.

## Known limits

- Regex usage scan: imports built from variables, code generated at build time and usage from
  outside the package (CI, Docker) are invisible — that is why `DC-UNUSED` is always triaged.
- Runtime edges in the component map come from `localhost:<port>` references and the ports a
  package serves (`-p` / `--port` in scripts, `*PORT … <n>` in source); remote URLs are not mapped.
- `evals/` reads `.claude/` by path; that link is not drawn.
- Sizes are apparent bytes on the current platform (platform-specific optional packages differ on
  macOS / CI).
